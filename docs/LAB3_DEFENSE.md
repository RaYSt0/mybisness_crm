# Лабораторная работа №3: серверное программирование

## Что требует работа

В методичке требуется добавить на сайт серверную функциональность: обработку данных и изменение результата на странице. Разрешён любой язык и среда; PHP/MySQL указаны как рекомендация. В проекте использованы уже имеющиеся FastAPI и PostgreSQL.

## Что реализовано

1. Frontend отправляет данные бизнеса и выбранную категорию в FastAPI. Backend создаёт организацию и возвращает её ID.
2. После подтверждения настройки frontend сохраняет структуру рабочего пространства в PostgreSQL. Backend проверяет формат, ограничивает размер конфигурации и увеличивает её версию при каждом сохранении.
3. Раздел клиентов получает записи с сервера, умеет добавлять клиентов; данные привязаны к организации. Backend проверяет входные данные, ищет, обновляет и удаляет записи через API.
4. Dashboard запрашивает серверную сводку: общее число клиентов, активные, новые и требующие внимания. Эти значения считаются SQL-запросом по данным выбранной организации, поэтому меняются после добавления или изменения клиента.
5. Если API отключено или недоступно, frontend показывает понятное сообщение и продолжает работать на локальных демонстрационных данных.

## Где смотреть код

- `backend/app/api/routes/clients.py` — HTTP маршруты клиентов.
- `backend/app/api/routes/workspace.py` — сохранение конфигурации и серверная сводка dashboard.
- `backend/app/schemas/client.py`, `workspace.py` — проверки входных и выходных данных.
- `backend/app/models/client.py`, `workspace_configuration.py` — таблицы SQLAlchemy.
- `backend/app/repositories/clients.py`, `workspace.py` — запросы к PostgreSQL.
- `backend/app/services/clients.py` — проверка организации и обработка отсутствующих записей.
- `frontend/src/app/product/workspaceApi.ts` — HTTP клиент frontend.
- `frontend/src/app/state/workspace-context.tsx` — связывает страницы с API и локальным режимом.

Путь запроса клиента:

```text
Форма FlowBiz → workspaceApi.addClient → POST /api/v1/organizations/{id}/clients
→ Pydantic ClientCreate → clients service/repository → таблица clients
→ JSON-ответ → список клиентов и пересчёт dashboard-summary
```

## Как показать преподавателю

1. Запустить PostgreSQL и FastAPI, затем frontend. В Swagger открыть `http://127.0.0.1:8001/docs`.
2. В приложении пройти onboarding и подтвердить рабочее пространство. Показать, что конфигурация сохраняется на сервере.
3. Открыть в Swagger `POST /organizations/{organization_id}/clients` и добавить клиента со статусом `new`.
4. Вызвать `GET /organizations/{organization_id}/dashboard-summary`: сервер вернёт `total_clients`, `active_clients`, `new_clients`, `attention_clients`.
5. Обновить FlowBiz: клиент появится в таблице, а значение показателя клиентов на главной изменится. Добавить второго клиента через интерфейс — он появится в PostgreSQL и сводка обновится.
6. Для демонстрации валидации отправить пустое имя клиента и показать HTTP 422. Для отсутствующего ID показать HTTP 404.

## Что сказать о решениях

«Серверная часть нужна, чтобы хранить общие данные бизнеса вне браузера и рассчитывать актуальные показатели. React вызывает HTTP API через отдельный сервисный слой, FastAPI валидирует запрос, сервис проверяет организацию, репозиторий работает с PostgreSQL. Поэтому интерфейс не содержит SQL и может заменить локальные mock-данные серверными ответами».

«Данные клиента содержат `organization_id`; все операции поиска и изменения ограничиваются ID организации. Это демонстрационная изоляция данных, но в проекте ещё нет входа пользователя и авторизации, поэтому в production нельзя считать один ID организации полноценной защитой доступа».

## Запуск и проверки

Команды запуска находятся в корневом `README.md` и `backend/README.md`. Автоматические backend-тесты используют SQLite in-memory, а не рабочую PostgreSQL базу; они проверяют API, валидацию и разделение организаций. Для защиты стоит отдельно показать ручной обмен frontend ↔ FastAPI ↔ PostgreSQL через браузер и Swagger.

## Ограничения

Реальный сервер сейчас хранит организации, конфигурацию и клиентов. Расписание, платежи, документы, задачи и автоматизации остаются демонстрационными данными. Регистрационная форма не создаёт учётную запись и не отправляет пароль: полноценную аутентификацию нужно делать отдельной работой. Автоматическое создание таблиц через SQLAlchemy `create_all` подходит локальному учебному прототипу; для обновления production-схемы нужны Alembic-миграции.
