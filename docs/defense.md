# Защита лабораторной №1: МойБизнес CRM

## Сначала разберись в границах проекта

Цель первой лабораторной — интерфейс и каркас frontend. В этой версии действительно работают маршрутизация, создание и редактирование учеников, архив и восстановление, поиск, переключение модулей и сохранение в браузере. Сервер, PostgreSQL, вход в аккаунт, реальные платежи, расписание и загрузка документов пока отсутствуют. Не называй макеты готовыми серверными функциями.

Используй текст ниже как план объяснения после знакомства с кодом. Если спрашивают о происхождении решения, отвечай честно: проект начинался с экспорта Figma и дорабатывался с ИИ-помощью. Не заявляй самостоятельное написание того, что ты не писал или пока не можешь объяснить.

## Вступление на 30–40 секунд

«МойБизнес CRM — приложение для небольшой школы танцев, спортивной секции или учебного центра. Сценарий начинается с регистрации владельца и создания персональной CRM: пользователь задаёт имя, название бизнеса, тип и нужные модули. Эти данные применяются к шапке, меню и главной странице. Для первой лабораторной реализован frontend на React и TypeScript: несколько экранов, клиентская маршрутизация, готовые UI-компоненты и мобильная вёрстка. Ученики и настройки сохраняются в браузере. Сервер будет подключён на следующих этапах».

## Демонстрация на 4–6 минут

1. **Регистрация и создание CRM.** Открой приложение в чистом браузере. Заполни имя владельца, email, название бизнеса, выбери тип и модули. Скажи: «До завершения анкеты рабочие страницы перенаправляют в онбординг. После завершения название применяется к интерфейсу и конфигурация сохраняется в браузере».
2. **Главная.** Покажи имя созданной CRM в меню и счётчики. Скажи: «Количество активных учеников и групп рассчитывается по текущему списку. Уведомления и графики пока демонстрационные».
3. **Ученики → Добавить ученика.** Введи вымышленное имя «Анна Соколова», группу «Группа Б» и дополнительные поля. Покажи отказ при имени из пробелов или будущей дате рождения. Сохрани корректную запись.
4. **Карточка.** Обрати внимание на URL `/students/<id>`. Обнови страницу: запись сохранилась. Открой редактирование, поменяй группу, сохрани. Объясни, что ID остаётся прежним, меняются поля той же записи.
5. **Архив.** Нажми «В архив», вернись к списку: ученик исчез из активных. Выбери «В архиве», открой его и восстанови. Покажи поиск по имени или группе. Архив не удаляет данные.
6. **Настройки CRM.** В «Настройках» открой «Изменить модули CRM», выключи «Финансы». Пункт исчезнет из меню. Обнови страницу — настройка сохранится. Прямой адрес `/finance` покажет объяснение выключенного модуля. Это настройка интерфейса, а не защита данных.
7. **Карточка → вкладки и настройки.** У исходного ученика покажи примеры посещений и платежей; у нового история пустая. В настройках выбери сотрудника и покажи права роли. Объясни, что реальное разграничение доступа появится на сервере.
8. **Мобильный экран и материалы.** Сузь окно: меню перестраивается, карточки идут в колонку, широкие таблицы прокручиваются. Покажи `docs/screenshots`, README и команды проверки.

Для предсказуемой демонстрации используй отдельный браузерный профиль или приватное окно и вымышленные данные. Не очищай сохранённые данные рабочего браузера без необходимости.

## Как проходит одно сохранение

Поле формы меняет локальное состояние `details` через `setDetails`. При submit браузер проверяет HTML-ограничения (`required`, `type=email`), обработчик отменяет обычную отправку страницы через `preventDefault`, убирает крайние пробелы и проверяет обязательные поля и дату. Затем вызывает `addStudent` или `updateStudent` из контекста.

При добавлении генерируется ID через `crypto.randomUUID`. Контекст создаёт новый массив, сериализует его в JSON и пытается записать в localStorage. Затем обновляет состояние React. После перехода на адрес карточки `useParams` возвращает ID, компонент находит нужную запись в общем массиве и показывает её. При перезагрузке Provider снова читает JSON из браузера.

Если запись в браузер не удалась, новое состояние остаётся в памяти, но появляется явное сообщение, что после перезагрузки изменения потеряются. Повреждённые исходные данные не перезаписываются просто при открытии страницы; предупреждение объясняет, что следующее сохранение заменит их.

## Вероятные вопросы

**Почему React?** UI разбит на компоненты. При изменении состояния React обновляет отображение. Общие шапка, навигация и кнопки переиспользуются на разных экранах.

**Зачем TypeScript?** Он проверяет типы при разработке: например, какие поля есть у Student и какие свойства принимает компонент. В браузере типов TypeScript уже нет, поэтому JSON из localStorage проверяется отдельной функцией `isStudent`.

**Что такое SPA и клиентская маршрутизация?** Приложение загружается в одну HTML-страницу. React Router связывает адрес с компонентом и переключает содержимое без полной загрузки документа при внутренних переходах. До завершения онбординга `Navigate` перенаправляет рабочие адреса на `/onboarding`. Обновление страницы остаётся обычным запросом к серверу, поэтому хостингу нужен fallback на index.html.

**Зачем Link вместо обычного a?** Link используется для переходов между страницами приложения через роутер. NavLink дополнительно позволяет оформить активный пункт. Обычная ссылка подходит для внешнего адреса или якоря.

**Что такое props, state и Context?** Props передают данные в компонент. State хранит изменяемые данные компонента. Context предоставляет один общий список учеников разным экранам без передачи через каждый промежуточный компонент.

**Почему нельзя просто менять массив через push?** Здесь операции создают новый массив через spread или map и передают его в setState. React получает новое значение состояния; такой подход также позволяет избежать случайных изменений старых данных.

**Зачем стабильный ID и key?** ID обозначает запись независимо от имени и порядка списка. По нему открывается карточка и обновляются данные. key помогает React сопоставлять элементы списка между рендерами; индекс списка для редактируемых записей хуже подходит.

**Это полноценная база данных?** Нет. localStorage хранит строки в одном браузере для одного origin. Здесь используется JSON. Нет совместной работы, резервного копирования или серверных прав. Очистка данных браузера удалит записи.

**Почему архивирование вместо удаления?** Оно обратимо и сохраняет карточку. Активный список исключает записи с archived=true; фильтр архива их показывает. Восстановление меняет флаг обратно.

**Как используется UI-библиотека?** Компоненты shadcn/ui находятся в проекте как исходники. Button, Input, Card и Switch задают общие элементы; Button и Switch используют Radix UI. Tailwind и переменные темы отвечают за оформление. Неиспользуемые компоненты удалены.

**Скрытый пункт меню защищает данные?** Нет. Это условный рендеринг по выбранным модулям. В будущем API должен проверять авторизацию и права независимо от frontend.

**Что проверяют тесты?** Реальные переходы и действия в Chromium: формы, ошибки, сохранение после обновления, архив и восстановление, вкладки, модули, прямые адреса и базовую адаптивность. Сборка отдельно проверяет TypeScript. Скриншоты служат материалом для визуальной проверки, сами по себе они не доказывают правильность поведения.

**Что дальше?** API на Python + FastAPI, PostgreSQL + SQLAlchemy, перенос операций хранения на сервер, серверная валидация и авторизация. Затем учёт расписания, посещений и абонементов. В текущей версии API-запросов ещё нет.
